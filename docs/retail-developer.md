# Sham Touch Retail — Permanent Developer Environment

**تحديث 8 نوفمبر 2026:** طلب المستخدم تصفير بيانات التجربة والتفعيل والمدير لاختبار الإعداد الأول. نُفذ التصفير بعد نسخة احتياطية خاصة؛ القاعدة والمهاجرات والمفاتيح محفوظة. الحالة الآن NOT_ACTIVATED، ولا يوجد مدير. افتح /register، فعّل الجهاز ثم أنشئ المدير من /setup-admin. تفاصيل الإعداد الأول أسفل هذا الملف تصف ما جرى سابقًا، وليست بيانات دخول حالية.


بيئة Developer جاهزة وتعمل محليًا:

- الواجهة: http://127.0.0.1:5196/inventory
- الكاشير: http://127.0.0.1:5196/sales
- Backend: http://127.0.0.1:37961
- PostgreSQL: `127.0.0.1:5432`، القاعدة الموجودة يدويًا `sham_retail_dev` فقط.
- الحساب: لا يوجد حساب بعد التصفير؛ ينشئ المستخدم حساب المدير بنفسه بعد التفعيل. الحساب القديم غير صالح.
- التفعيل: `NOT_ACTIVATED` بعد التصفير المطلوب. مفاتيح الاختبار القديمة محفوظة ولم تتغير.

البيئة محلية للتطوير، ولا تفعّل وضع Production أو تغيّر Windows Service/Installer أو نظام المطاعم. تُركت البيئة تعمل بعد التحقق لتتمكن من فتح الرابط مباشرة.

## التشغيل والإيقاف

من PowerShell أو Terminal:

```powershell
cd C:\Users\Iway\Desktop\retial
npm run dev
```

يشغّل ذلك Backend وVite في الخلفية، ويعرض الرابط. إغلاق Terminal أو واجهة المتصفح لا يعيد تهيئة القاعدة، ولا يلزم ترك نافذة أوامر مفتوحة. إذا كان التشغيل قائمًا، لا يُنشئ الأمر نسخة أخرى.

```powershell
npm run dev:status
npm run dev:stop
```

الإيقاف يغلق عمليتي Retail Developer فقط، ويحافظ على خدمة PostgreSQL والقاعدة وكل البيانات. عند تعارض المنافذ، يتوقف التشغيل برسالة ولا يقتل العملية التي تشغل المنفذ ولا يختار قاعدة أخرى.

## تسجيل الدخول

```powershell
npm run dev:login
```

بعد التصفير تعرض النافذة إرشادًا لاستخدام المدير الذي تنشئه من الواجهة. لا يوجد حساب مسبق ولا يُحفظ اختيارك الجديد في ملف كلمة مرور محلي تلقائيًا. الحساب السابق محفوظ فقط داخل النسخة الاحتياطية الخاصة للتراجع.

ملف معلومات الحساب المحلي: `.developer/login.json`. لا توزّع مجلد `.developer` أو تضعه في Git.

## الإعدادات والأسرار

أُدخلت بيانات PostgreSQL عبر نافذة محلية؛ لم تُفترض كلمة مرور. حُفظ الاتصال في `.developer/.env`، مع ترميز رموز كلمة المرور داخل URL بصورة صحيحة. الملف محلي محمي بصلاحيات Windows لحساب المستخدم وSYSTEM وAdministrators فقط، ومستثنى من Git. حماية ملف البيئة تعتمد على الصلاحيات، لا على ادعاء تشفير نص كلمة المرور داخله.

عند الحاجة لتغيير بيانات الاتصال:

```powershell
npm run dev:stop
npm run dev:configure
npm run dev:inspect
```

النافذة ترفض تغيير الاتصال أثناء تشغيل Developer. اسم القاعدة ثابت `sham_retail_dev`، ولا ينشئ أي أمر قاعدة بديلة. عند تغيير خادم PostgreSQL إلى قاعدة تحمل الاسم نفسه، يُطلب فحص ومراجعة هوية القاعدة بدل تشغيلها تلقائيًا كأنها القاعدة السابقة.

## فحص القاعدة والمهاجرات

فُحصت القاعدة قبل الكتابة في معاملة READ ONLY. كانت فارغة: بلا جداول أو تسلسلات أو دوال مستخدم أو بيانات أو مهاجرات سابقة. سُجل الفحص الأول في `.developer/initial-inspection.json`.

طُبّقت المهاجرات التسع الموجودة حتى المرحلة الرابعة بالترتيب، باستخدام `backend/src/db/migrate.js` نفسه دون تعديل SQL السابق:

1. `001_foundation.sql`
2. `002_stock_integrity.sql`
3. `003_catalog_search.sql`
4. `004_variant_combinations.sql`
5. `005_commercial_operations.sql`
6. `006_commercial_permissions.sql`
7. `007_advance_allocations.sql`
8. `008_limited_runtime_and_shift_history.sql`
9. `009_print_dispatch.sql`

أُنشئ النشاط والحساب الأول عبر خدمة bootstrap القائمة، دون Seed أو Reset أو حذف. لم تُنشأ قاعدة PostgreSQL أو أدوار PostgreSQL جديدة؛ استُخدم الاتصال الذي أدخلته للقاعدة الموجودة.

```powershell
npm run dev:inspect
```

أمر فحص فقط: يسجل أسماء الجداول وعدد صفوفها وبصمات المهاجرات دون قراءة كلمات مرور الحسابات أو تعديل البيانات. يحتفظ الخادم بهوية القاعدة OID ويتحقق منها عند بدء التشغيل.

`npm run dev:setup` مخصص للإعداد الأول على قاعدة فارغة. التشغيل العادي لا يستدعيه ولا يستدعي migrations/bootstrap. إذا وجد أمر الإعداد بيانات غير مهيأة بواسطة هذا الملف المحلي، يتوقف للمراجعة دون تعديل. إعادة الأمر بعد اكتمال الإعداد لا تعيد كلمات المرور أو المفاتيح أو البيانات؛ اختُبر ذلك ببصمات الملفات. أي مهاجرات مستقبلية تحتاج مراجعة منفصلة؛ لا تُطبق تلقائيًا عند التشغيل اليومي.

## التفعيل التجريبي

استُخدمت الآلية الرسمية داخل المشروع: إنشاء طلب Retail لبصمة الجهاز الحقيقية، إصدار الكود عبر `activation-bridge/retail.cjs`، ثم التحقق والتفعيل عبر `createActivationService`. لم يُحقن ترخيص وهمي أو يُعطل فحص الترخيص أو الصلاحيات.

مفتاح Ed25519 التجريبي مستقل تمامًا عن مفاتيح الإنتاج. مفتاحه الخاص مشفّر ومحفوظ في `.developer/activation`، ومفتاح سلامة الترخيص في `.developer/runtime`. يُحمَّل المفتاح العام التجريبي عبر إعداد عملية Developer فقط، دون استبدال `backend/src/resources/retail-public-key.pem`.

الترخيص التجريبي للوظائف الأساسية، والميزات المتقدمة غير ممنوحة افتراضيًا. لا يُعاد إنشاء الترخيص أو المفاتيح عند التشغيل. عند انتهاء الترخيص التجريبي يلزم تجديده بالطريقة الرسمية ومفتاح الاختبار، وليس إلغاء التحقق منه.

## البيانات الدائمة والواجهة

تعمل الواجهة في وضع server بشكل صريح وتتصل بالـBackend الحقيقي عبر proxy. روابط inventory وsales تفتح Retail المتصل، وليست Demo القديم. بيانات المنتجات والفواتير والمشتريات والعملاء والمخزون والإعدادات تحفظها الخدمات التجارية القائمة داخل `sham_retail_dev`؛ لا توجد قاعدة جديدة لكل تشغيل أو استبدال بحالة المتصفح.

يحافظ الإغلاق وإعادة التشغيل على القاعدة وملفات التفعيل والهوية. لا تحذف `.developer` عند التنظيف؛ به إعداد الاتصال ومعلومات الدخول وسلامة الترخيص. خذ نسخة آمنة من القاعدة والإعدادات الخاصة عند الحاجة للنسخ اليدوي. أُزيل وضع Demo المنفصل وزر الدخول إليه وملفات بياناته التجريبية. الدخول الوحيد الآن يتطلب حساب الخادم، مع الاحتفاظ بالتصاميم المشتركة. بيانات المتصفح القديمة لا تُحمّل ولا تُنقل تلقائيًا إلى PostgreSQL.

## التغييرات الضرورية في كود النظام

تمت إضافة `package.json` في جذر المشروع، وملفات `developer/`، وقاعدة تجاهل `.developer/` في `.gitignore`.

التعديلات على النظام القائم اقتصرت على ما يلزم لتشغيل Developer وحمايته:

1. `backend/src/config.js`: السماح بالاسم المحدد `sham_retail_dev` فقط مع `RETAIL_DEVELOPER_MODE=true` و`NODE_ENV=development` وواجهة وخادم HTTP على loopback. لا يفتح الاستثناء قواعد المطاعم أو أسماء أخرى أو Production. يغطيه اختبار مستقل.
2. `frontend/vite.config.js`: منع تقديم أي ملف من `.developer` عبر خادم التطوير، مع الإبقاء على قواعد منع ملفات الأسرار الأصلية. نُقل cache الخاص بـDeveloper إلى `frontend/node_modules/.vite-developer` خارج المجلد الخاص حتى تظل ملفات الواجهة قابلة للتحميل.
3. `frontend/src/commercial/ServerPOS.jsx`: إصلاح حجز Web Lock أثناء إعادة تشغيل effects التي يجريها React StrictMode في التطوير؛ كانت نافذة واحدة تُرفض خطأ كنافذة ثانية. بقي StrictMode مفعّلًا وبقي منع النافذتين فعالًا. جُرّبت النافذة الأولى والثانية فعليًا في المتصفح.

لم تُعدّل المهاجرات أو حسابات النظام الأخرى أو قواعد المطاعم، ولم يُلمس `pos-offline` في هذا الإعداد، ولم تُعدّل ملفات Installer أو Windows Service أو مفاتيح الإنتاج. حُفظت تغييرات المشروع السابقة الموجودة قبل هذه المهمة.

## نتائج التحقق

- نجح الاتصال بالقاعدة المطلوبة نفسها، وفحص فراغها قبل أي كتابة.
- نجحت المهاجرات التسع والتحقق من بصماتها عند بدء Backend.
- نجح تسجيل الدخول بالحساب الجديد وقراءة حالته عبر API الحقيقي.
- نجح التفعيل الرسمي التجريبي وأصبحت حالته `ACTIVE`.
- ظهرت شاشة المنتجات والكاشير المتصل بالخادم، دون الدخول إلى Demo.
- حُفظ منتج تجريبي واحد، بسعر 7.5 ورصيد مخزني صفر، عبر API الحقيقي.
- أُغلق Chromium بالكامل، ثم أُوقف Backend وFrontend بالأمر الرسمي وأُعيدا تشغيلهما.
- ظهر المنتج نفسه بقيمه بعد إعادة تشغيل Backend وبعد إعادة فتح المتصفح.
- منعت نافذة كاشير ثانية، واستمرت النافذة الأولى بصورة صحيحة تحت StrictMode.
- رُفضت طلبات HTTP لملفات `.developer/.env` و`login.json` وبيانات الوصول لمفتاح الاختبار بحالة 403.
- بقي عدد المستندات التجارية كما كان؛ لم تُفتح وردية ولم تُنشأ مبيعات أو مشتريات أو سندات تلقائية.
- لم يتغير حساب المدير أو مفاتيح التفعيل عند إعادة أمر الإعداد.
- نجح اختبار قيد قاعدة Developer، وBackend lint/build، وFrontend build، واختبارات Frontend الستة عشر.
- Frontend lint بلا أخطاء مع ثمانية تحذيرات قديمة من المرحلة السابقة؛ لم تُجر تعديلات لا تتصل بطلب Developer لمعالجتها.

يمكن إعادة اختبار الاحتفاظ بالمنتج نفسه دون بيع:

```powershell
npm run dev:verify
```

يعيد هذا الأمر تشغيل Developer ويختبر متصفحًا خاصًا وملفات الحماية. يعيد استخدام منتج التحقق المسجل ولا يمسح البيانات أو يعدل منتج التحقق إذا وجد أنه تغير. النتيجة والصور محفوظة في `.developer/verification/`.
